# Benchmark: a 1,000-page library (2026-11-03)

How Faber holds up with a realistic amount of browsing: indexing speed, search speed,
whether the first result is the page you meant, and what the app looks like full.

**Setup:** MacBook (Apple Silicon), Ollama, `qwen3:4b` for summaries, `qwen3-embedding:0.6b`
for embeddings, daemon 0.1.3 plus the fixes below. Library: 1,012 docs (1,000 crawled pages
+ 12 existing), 5,406 chunk vectors.

## Results at a glance

| | Before (0.1.3) | After this work |
|---|---|---|
| Search, live over HTTP (hybrid, p50) | 439 ms | **70 ms** (~40 ms repeated query) |
| Keyword search (p50) | 365 ms | **26 ms** |
| Browse, no query (p50) | 269 ms | **9 ms** |
| Facets for a query (p50) | 889 ms | **243 ms** |
| Right page is the first result | 74% | **84%** |
| Right page in the top 3 | 90% | **94%** |
| Right page in the top 10 | 97% | **100%** |

## How the test works

`scripts/bench/` has the tools; results go to `~/.faber/bench/`.

1. **`crawl.ts`** reads RSS feeds (BBC, NYT, Guardian, NPR, Ars Technica, The Verge, Wired,
   Al Jazeera) and the Hacker News API, fetches each article and extracts its text, and gives
   it a believable browsing history: first visit after publication, then a few revisits for
   some (Zipf-distributed). Pages go in through `/api/capture`, the same path the extension uses.
   1,000 pages in 27 s; capture p50 10 ms, p95 68 ms. Sites: Guardian 221, BBC 221, NYT 220
   (feed text only: articles block bots), HN 189, Wired 50, Ars 35, NPR 29, Al Jazeera 25, Verge 10.
2. **`monitor.ts`** samples queue progress and a probe search every 20 s while indexing.
3. **`run.ts`** builds three kinds of query per sampled page and records latency and recall:
   - *title*: a few words from the title ("supermarket freezers suspected cyber-attack");
   - *gist*: how you'd describe it from memory, written by the model from the summary
     ("supermarket cyber attack refrigerators defrost mode europe");
   - *detail*: words from deep in the text you might half-remember ("French-owned 15 Belgian carrefour").
   435 queries. hit@1 = the page is the first result.
4. **`rank-lab.ts`** re-implements ranking offline with every knob exposed and scores variants
   against the same queries on a copy of the library.
5. **`ui.ts`** drives the web app with Playwright: load times, time from last keystroke to
   results, ⌘K launcher, DOM size, screenshots.
6. **`report.ts`** prints a markdown comparison of every run.

Re-run:

```sh
bun scripts/bench/crawl.ts            # fills the *current* library: use a test FABER_HOME or back up first
bun scripts/bench/monitor.ts &         # while it indexes
bun scripts/bench/run.ts --label <name>
bun scripts/bench/ui.ts --label <name>
sqlite3 ~/.faber/faber.sqlite ".backup /tmp/lib.sqlite" && bun scripts/bench/rank-lab.ts /tmp/lib.sqlite
bun scripts/bench/report.ts
```

## Indexing

- 1,000 pages summarised and embedded in 3.5 h with benchmarks competing for the model,
  **~10 pages/min (6 s/page) when left alone**. Per page: summary p50 7.2 s, p90 11.9 s, max 42 s.
- A page visited during the backlog was keyword-searchable (rank 1) 53 ms after capture
  and summarised within 5 s: new visits jump the queue.
- Search while indexing: p50 402 ms, p90 772 ms, max 4.1 s (measured before the speed fixes;
  the model and the database compete for the same machine).
- Bug found and fixed: documents queued before their text arrived (Chrome history imports of
  Google Docs) were never processed and showed as "pending" forever.

## Search speed

Wall clock from the client, ms, p50 / p90.

| run | docs / enriched | hybrid | keyword | semantic | while typing | browse | facets (query) |
|---|---|---|---|---|---|---|---|
| 1 captured, not indexed | 1011 / 20 | 134 / 190 | 121 | 34 | 125 / 175 | 20 | 254 |
| 2 fully indexed (0.1.3) | 1012 / 1011 | 439 / 544 | 365 | 335 | 412 / 487 | 269 | 889 |
| 3 speed fixes | 1012 / 1011 | 63 / 80 | 29 | 38 | 77 / 116 | 13 | 470 |
| 4 speed fixes + ranking | 1012 / 1011 | 70 / 87 | 26 | 37 | 76 / 106 | 9 | 243 |

Search slowed down ~3× as summaries arrived. Profiling on a copy of the library found:

1. **Every search rebuilt every project.** Results are labelled with their projects, and
   working that out re-grouped the whole library (all summaries, all corrections): 40 ms at
   1,000 docs and growing linearly. Now cached until the next database write.
2. **Snippets for every candidate.** `snippet()` was most of the cost of a keyword query, and
   it ran on 60 candidates to show 20. Now computed only for the results returned
   (keyword 53 → 4 ms in-process).
3. **Facets threw the cache away.** Scoping facet counts to the results wrote a temp table,
   which counts as a write. Now a read-only JSON parameter; facets also skip snippets.

In-process (no HTTP): hybrid 60 → 10 ms, keyword 53 → 4 ms, browse 76 → 2 ms, loading 60 docs 40 → 1 ms.

## Is the first result the right one?

| run | mode | title | gist | detail | all hit@1 | hit@3 | hit@10 |
|---|---|---|---|---|---|---|---|
| 2 (0.1.3) | hybrid | 85% | 96% | 42% | 74% | 90% | 97% |
| 2 (0.1.3) | keyword | 88% | 89% | 72% | 83% | 95% | 98% |
| 2 (0.1.3) | semantic | 61% | 87% | 14% | 54% | 67% | 73% |
| 4 tuned | **hybrid** | **94%** | **95%** | **61%** | **84%** | **94%** | **100%** |
| 4 tuned | keyword | 95% | 93% | 70% | 86% | 97% | 100% |
| 4 tuned | semantic | 81% | 92% | 16% | 63% | 70% | 74% |

In 0.1.3, hybrid (the default) was *worse* than keyword alone. Semantic search finds
paraphrases, but its near-misses pushed exact keyword matches off the top, and the
frequent-use boost (0.3) let favourites outrank better matches.

Variants tried offline (`rank-lab.ts`, hit@1 all / detail):

| variant | all | detail |
|---|---|---|
| 0.1.3 | 74% | 42% |
| no use boosts | 79% | 52% |
| title-coverage boost 0.3 | 77% | 41% |
| semantic weight 1.5 | 72% | 36% |
| RRF k = 60 | 74% | 34% |
| semantic weight 0.5 | 83% | 60% |
| semantic 0.5 + content weight 3 + title coverage 0.3 | 84% | 60% |
| semantic 0.3 + content 3 + title coverage 0.3 | 85% | 62% |
| **shipped:** semantic 0.5, content 3, title coverage 0.3, habit 0.15, recency 0.05 | **84%** | **61%** |

The shipped settings keep a real frequent-use boost (halving it cost nothing measurable) and
leave semantic at 0.5 rather than 0.3: the benchmark's *detail* queries are random words from
the text, which favour keyword by construction, and real vague-memory queries need semantic more.

While the library is still being indexed, ranking is worse (run 1: 36% hit@1): docs with
vectors get two chances to score and outrank better keyword matches that aren't embedded yet.

## The app with 1,000 pages

From `ui.ts` (median): home 6 ms, search page 9 ms, projects 11 ms, people 7 ms, ⌘K opens in
12 ms. Results appear ~150 ms after the last keystroke on the search page (200 ms debounce)
and ~113 ms in the launcher (120 ms debounce): the debounce is now most of the wait. The
search page renders ~9,000 DOM nodes.

Screenshots: `~/.faber/bench/screens/tuned-*.png`.

What looks wrong at this size:

- **972 projects from 1,012 web pages.** Project inference treats every news topic as a
  project ("octopus farming ban", "Texas Senate race"); the sidebar and Inbox (958) fill with noise.
- **2,081 people.** Everyone named in a news story becomes a person.
- **Work-document types on news.** 93 articles are "postmortem", 260 "policy", 448 "research".
- **Site chrome in the index.** 106 pages contain navigation text ("Artificial
  intelligenceFollow Artificial intelligence") that matches searches and shows as the snippet.
- **Near-duplicate tags.** `#ai-data-centers` and `#ai-data-centres`.

## Ask

Five questions about the library, same retrieval, two models (`~/.faber/bench/ask-models.json`):

| model | time per answer | answers that are just the model thinking aloud |
|---|---|---|
| `qwen3:4b` (current) | 26 s – 229 s (median 143 s) | 5 of 5 ("Let me analyze the question and the sources…", 3–8k chars) |
| `qwen3:4b-instruct` | 6 s – 13 s (median 10 s) | 0 of 5 (350–1,700 chars, cited) |

`qwen3:4b` (the "thinking" build) ignores `think: false` and writes its reasoning into the
answer. Summaries are unaffected because they use a JSON schema, which forces a clean
answer; Ask asks for prose, so it isn't protected. Example from the instruct model:
"The Reserve Bank of Australia (RBA) decided to increase the official cash rate to 4.85%, its
highest level since 2008, marking a fifth hike in 2026 [1]."

## Suggestions, most valuable first

**Ask**

- **Use `qwen3:4b-instruct` for Ask** (and offer it as the default in `faber models` and
  Settings): 15× faster and readable. Stream the answer so the first words show in ~1 s.

**Find it immediately (recall and freshness)**

1. **Embed at capture, summarise later.** A new page is keyword-searchable at once but only
   gets vectors after its summary (6–12 s, hours during a backlog). Embed the raw text at
   capture (tens of ms per chunk) and re-embed with the summary later. This also removes the
   embedded-vs-not ranking bias while indexing.
2. **Until then, don't let embedded docs outrank unembedded ones**: count an unembedded doc's
   keyword rank twice (fill the missing semantic list). Run 1: title hit@1 54% → 96% offline.
3. **Strip site chrome before indexing** (nav, "Follow" links, footers): better snippets,
   fewer false matches, smaller index.
4. **Detail recall (61%)**: a second keyword pass over content-only matches (phrase or
   NEAR queries) and chunk-level BM25 instead of whole-document.

**Snappy**

5. **Lower the debounce** to ~60 ms (search page) / ~40 ms (launcher), now that a search
   takes 30 ms, and cancel stale requests.
6. **Show keyword results first and let semantic results join.** Keyword is ~4 ms in-process;
   embedding the query costs ~25 ms more on a cold query and seconds while Ollama is busy
   summarising. Time-box semantic (~150 ms) so search never waits on the model.
7. **Share one search between results and facets.** Facets re-run the search (243 ms for 500
   results); compute them from the same hits.
8. **Virtualise long result lists** (9,000 DOM nodes on the search page).
9. **Indexing priority by recency of visit at claim time**, not at enqueue time, so a backlog
   of old multi-visit pages never delays what you just saw.

**Relevance of what's shown**

10. **Make project inference stricter for web pages**: a project needs two or more docs, or
    work sources (Docs/Slides/Sheets), or confirmation. Same for people (seen in ≥2 docs or in
    a work doc).
11. **Add an "article" document type** and use it for news and blogs.
12. **Normalise tag spellings** (US/UK spelling, plurals) when saving tags.

**Indexing speed**

13. **Smaller input for summaries** (lower `max_chars`) and a non-thinking model:
    summary time is dominated by input length on a 4B model.
14. **Summarise two at a time** when the machine is idle (Ollama `OLLAMA_NUM_PARALLEL`).
